⚠ The Problem

Modernising a Java Monolith is Hard

Enterprises running large Spring Boot monoliths face mounting pressure to migrate to microservices — but the journey from "one big WAR file" to clearly-bounded services is filled with hidden complexity, risk, and manual toil.

🧩

Tangled Codebases

Hundreds of Java classes share database connections, Spring beans, and `@Transactional` boundaries with no clear ownership or domain separation.

⏱

Months of Manual Analysis

Teams spend weeks reading code, drawing diagrams, and debating service boundaries — all before writing a single line of the new architecture.

🔗

Invisible Coupling

Static code analysis misses runtime co-change coupling revealed only by Git history: classes that always change together belong together.

🧨

Transactional Risk Blindspots

`@Transactional` boundaries that cross what would become service boundaries introduce distributed-transaction problems that are expensive to fix post-migration.

📐

No Extraction Order

Even when boundaries are agreed, teams have no principled ordering: which service to extract first? What are the blockers? What patterns apply?

🔑

High Expertise Barrier

Effective decomposition requires domain experts, architects, and senior engineers working together — talent that is scarce and expensive to assemble.

✦ The Solution

How MicroMorphAgent Addresses It

Point the agent at any public or private Spring Boot GitHub repository. In minutes, it returns a comprehensive decomposition plan backed by code-level analysis and LLM reasoning.

✓
Automated static analysis

Lezer Java AST parser extracts every class's annotations, imports, layer, and type references in-browser — no server, no upload.

✓
Git co-change mining

Analyses up to 200 recent commits; builds a co-change matrix that surfaces behavioural coupling invisible to dependency analysis alone.

✓
LLM-driven bounded context identification

Sends package summaries + co-change signals to an LLM; receives named candidate microservices with packages, entities, APIs, risk scores, and rationale.

✓
Transactional risk detection

Identifies `@Transactional` methods whose outbound dependencies cross proposed service boundaries, ranked by severity with mitigation patterns (Saga, outbox, etc.).

✓
Ordered extraction roadmap

LLM generates a step-by-step extraction plan ordered by coupling score, with effort estimates, blockers, and recommended patterns per step.

✓
Maven module scaffolding

Per-service Maven module layouts generated automatically, so teams start the migration with real project structure in hand.

⚙ How It Works

Six-Phase Analysis Pipeline

Each analysis run executes six sequential phases in a real-time dashboard with live activity logging.

1
POM Discovery
Parse pom.xml for groupId & module metadata
2
Code Ingestion
Download all .java files via GitHub Contents API
3
Graph Construction
Build class dependency graph + co-change matrix
4
AI Summarisation
LLM produces semantic package descriptions
5
Decomposition Reasoning
LLM identifies contexts, roadmap, risks & modules
6
Report
Interactive multi-panel report rendered in browser

Three Analysis Modes

Choose the mode that matches your available credentials.

AI Mode

Full AI Analysis

All six phases run with LLM calls via OpenRouter. Requires a GitHub PAT and an OpenRouter API key. Most thorough output.

Requires: GitHub Token + OpenRouter Key
Static Mode

Heuristic Analysis

Phases 1–3 run normally; bounded contexts derived from namespace grouping and coupling scores. No API key needed.

Requires: GitHub Token only
Demo Mode

Zero-Credential Demo

Runs against a synthetic Spring PetClinic dataset. Explore the full UI and all output panels without any tokens.

Requires: Nothing

Zero-Backend Privacy Model

Your source code never leaves the browser. Java files are fetched directly from the GitHub API using your token, parsed in-memory with a WebAssembly-compiled Lezer parser, and all graphs are built client-side. The only data forwarded externally are the per-package summaries (class names, annotations, cross-package imports) sent to your chosen OpenRouter LLM over HTTPS. Credentials live only in localStorage and are never transmitted to any server operated by this app.
